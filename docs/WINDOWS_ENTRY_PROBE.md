# Windows entry diagnostic

This artifact is a CPU entry diagnostic, **not a playable port**. It maps an
unlinked image, applies its relocations, and attempts the original x86-64 entry.
Startup contracts currently include the observed USA 1.03 `_init_env` return,
`atexit` callback registration, a Windows-generated stack canary and event queue
creation/deletion and GPU event subscriptions. Subscriptions are stored and can
be removed; an explicit completion hook can mark them pending. No renderer is
connected to that hook, and waiting remains unresolved. This is not functioning
GPU synchronization. Resolution
also covers mutex attributes, creation, locking, try-lock, ownership checks,
recursive locking, unlocking and destruction. Static lazy initialization, timed
locks, condition-variable waiting/signaling and priority scheduling remain unresolved.
Condition attributes and explicit condition creation/destruction are implemented.
Resolution
requires preparation evidence and the observed exact import scopes. The libc
`_init_env` implementation was verified as exactly RET. Registered callbacks run
in reverse order on normal guest termination; C++ destructor registrations preserve
their arguments and DSO identities. Scoped `__cxa_finalize` is not implemented;
diagnostic failures skip all callbacks.
Other function and data imports remain unresolved. There is no complete
PS4 runtime, graphics or audio. Native library initialization and Windows TLS are
available only in the experimental linked-image mode described below.
A failure or an early unsupported import is an expected diagnostic result.

## Build on GitHub

The `Windows entry diagnostic` workflow builds with MSYS2 CLANG64 on Windows,
runs synthetic tests without any game files, and uploads the
`tlg-windows-entry-diagnostic` artifact. Pushes to `the-last-guardian` trigger it.
It can also run manually when the workflow is available on the default branch.
No game files, credentials, boot images, or local inspection outputs are packaged.

## Run locally

Extract the artifact and use Windows Python 3.10 or newer. From its folder:

```powershell
python scripts/prepare_tlg.py 'D:\path\to\CUSA03627'
.\tlg-entry-probe.exe .\out\tlg\boot-windows.bin
```

Use **boot-windows.bin** (`TLGWIN01`), which carries complete import identities.
The legacy unlinked `boot.bin` is retained for diagnostics; never use
`boot-linked.bin`, which contains Linux TLS rewrites.
Preparation accepts only the observed USA 1.03 image and bundled module hashes.
The original game files are read only. The generated files remain local.
Do not run the inherited Bloodborne launcher, patch scripts or `run.sh` on TLG.

The probe prints its result to the terminal. Exit 20 means the first unsupported
function import was reached; 23 means a Windows exception (including a data import
access or unimplemented guest TLS); 24 means the guest exit callback was reached;
124 is the ten-second watchdog; 1 is an input/loader error or unexpected return.
None of these outcomes proves the game boots or plays. The preparation flag is
evidence carried in a local diagnostic file, not cryptographic authentication:
only execute files generated by the provided target validation scripts.

The corresponding diagnostic source and preparation scripts are included with
the GNU GPL license. Full project attribution remains in the repository.

## Experimental native-module mode

Preparation also generates `out/tlg/boot-windows-linked.bin` (`TLGWIN02`). Run it
with the same diagnostic executable to attempt libc/Fios2 initialization before
game entry. The loader validates native bindings, module/TLS ranges and original
TLS pattern bytes, then applies Windows TEB-slot displacements in memory.
It configures per-thread module TLS and invokes initializers in dependency order.
Pattern matching is inherited; complete instruction-boundary analysis is pending.

The observed USA 1.03 libc initializer starts, obtains process parameters and
registers its application heap interface, queries shared heap-trace structures
and the explicit base-PS4 profile, then stops at `sceKernelGetDirectMemorySize`.
It has not returned successfully;
Fios2 initialization and the game entry have not run in this mode.
The unlinked mode still reaches `strlen`. Neither result proves gameplay support.


### Direct-memory backend (October 13, 2026)

The Windows diagnostic now exposes a 5056 MiB retail PS4 direct-memory budget,
with synchronized physical allocation accounting and independent pagefile-backed
sections. Complete allocations can be mapped multiple times below 1 TiB; aliases
share actual storage. Allocation alignment, overlap, bounds, stale releases and
mapped-allocation lifetime are checked. The section commits backing storage for
allocated bytes, rather than committing the entire advertised pool up front.

This initial mapping contract accepts CPU read/write protection (`3`), zero flags,
no requested address, and complete allocations only. Fixed mappings, subranges,
GPU protections, partial unmapping and releasing mapped allocations are not yet
supported. Unsupported requests return an error; no renderer is connected.
Address placement has a bounded search and can fail under fragmentation.

Validation: 17 Windows entry tests pass, including a synthetic test that writes
through one alias and reads the same bytes through another. With the validated
USA 1.03 native image, execution passes the direct-memory-size query and stops at
`sceKernelMapFlexibleMemory` (`IWIBBdTHit4`, caller offset `0x207dbc`) during libc
initialization. Original game entry, graphics and the menu remain untested.


### Flexible memory (October 13, 2026)

Flexible memory now has a separate 448 MiB budget backed by zero-initialized
private Windows allocations. Supported CPU protections are translated to Windows
page protections. Mapping without a placement flag chooses a low address; fixed
mapping (`0x10`) supports free ranges aligned to Windows' 64 KiB reservation
granularity. Existing mappings are never replaced. GPU protection bits, occupied
fixed ranges and partial release remain unsupported. Both the flexible-specific
release and generic unmap update the budget only after a successful host release.
Named mappings share the same implementation; names are diagnostic metadata only.

The 17 Windows entry tests pass, with additional checks for zero-fill, allocation
isolation, budget rejection, fixed address placement, collision rejection and
stale/incorrect releases. The actual USA 1.03 libc initialization successfully maps
293601280 bytes (280 MiB) at its requested fixed address. The next unsupported call
is `scePthreadAttrInit` (`nsYoNRywwNg`, caller offset `0x5b42958`). Native module
initialization is still incomplete; original game entry and the menu have not run.
