# Windows entry diagnostic

This artifact is a CPU entry diagnostic, **not a playable port**. It maps an
unlinked image, applies its relocations, and attempts the original x86-64 entry.
Startup contracts currently include the observed USA 1.03 `_init_env` return,
`atexit` callback registration, a Windows-generated stack canary and event queue
creation/deletion and GPU event subscriptions. Subscriptions are stored and can
be removed; an explicit completion hook can mark them pending. No renderer is
connected to that hook, and waiting remains unresolved. This is not functioning
GPU synchronization. Resolution
also covers mutex attributes, creation, locking, try-lock, ownership checks,
recursive locking, unlocking and destruction. Static lazy initialization, timed
locks, condition-variable waiting/signaling and priority scheduling remain unresolved.
Condition attributes and explicit condition creation/destruction are implemented.
Resolution
requires preparation evidence and the observed exact import scopes. The libc
`_init_env` implementation was verified as exactly RET. Registered callbacks run
in reverse order on normal guest termination; C++ destructor registrations preserve
their arguments and DSO identities. Scoped `__cxa_finalize` is not implemented;
diagnostic failures skip all callbacks.
Other function and data imports remain unresolved. There is no complete
PS4 runtime, graphics or audio. Native library initialization and Windows TLS are
available only in the experimental linked-image mode described below.
A failure or an early unsupported import is an expected diagnostic result.

## Build on GitHub

The `Windows entry diagnostic` workflow builds with MSYS2 CLANG64 on Windows,
runs synthetic tests without any game files, and uploads the
`tlg-windows-entry-diagnostic` artifact. Pushes to `the-last-guardian` trigger it.
It can also run manually when the workflow is available on the default branch.
No game files, credentials, boot images, or local inspection outputs are packaged.

## Run locally

Extract the artifact and use Windows Python 3.10 or newer. From its folder:

```powershell
python scripts/prepare_tlg.py 'D:\path\to\CUSA03627'
.\tlg-entry-probe.exe .\out\tlg\boot-windows.bin
```

Use **boot-windows.bin** (`TLGWIN01`), which carries complete import identities.
The legacy unlinked `boot.bin` is retained for diagnostics; never use
`boot-linked.bin`, which contains Linux TLS rewrites.
Preparation accepts only the observed USA 1.03 image and bundled module hashes.
The original game files are read only. The generated files remain local.
Do not run the inherited Bloodborne launcher, patch scripts or `run.sh` on TLG.

The probe prints its result to the terminal. Exit 20 means the first unsupported
function import was reached; 23 means a Windows exception (including a data import
access or unimplemented guest TLS); 24 means the guest exit callback was reached;
124 is the ten-second watchdog; 1 is an input/loader error or unexpected return.
None of these outcomes proves the game boots or plays. The preparation flag is
evidence carried in a local diagnostic file, not cryptographic authentication:
only execute files generated by the provided target validation scripts.

The corresponding diagnostic source and preparation scripts are included with
the GNU GPL license. Full project attribution remains in the repository.

## Experimental native-module mode

Preparation also generates `out/tlg/boot-windows-linked.bin` (`TLGWIN02`). Run it
with the same diagnostic executable to attempt libc/Fios2 initialization before
game entry. The loader validates native bindings, module/TLS ranges and original
TLS pattern bytes, then applies Windows TEB-slot displacements in memory.
It configures per-thread module TLS and invokes initializers in dependency order.
Pattern matching is inherited; complete instruction-boundary analysis is pending.

The observed USA 1.03 libc initializer starts, obtains process parameters and
registers its application heap interface, queries shared heap-trace structures
and the explicit base-PS4 profile, then stops at `sceKernelGetDirectMemorySize`.
It has not returned successfully;
Fios2 initialization and the game entry have not run in this mode.
The unlinked mode still reaches `strlen`. Neither result proves gameplay support.


### Direct-memory backend (October 13, 2026)

The Windows diagnostic now exposes a 5056 MiB retail PS4 direct-memory budget,
with synchronized physical allocation accounting and independent pagefile-backed
sections. Complete allocations can be mapped multiple times below 1 TiB; aliases
share actual storage. Allocation alignment, overlap, bounds, stale releases and
mapped-allocation lifetime are checked. The section commits backing storage for
allocated bytes, rather than committing the entire advertised pool up front.

This initial mapping contract accepts CPU read/write protection (`3`), zero flags,
no requested address, and complete allocations only. Fixed mappings, subranges,
GPU protections, partial unmapping and releasing mapped allocations are not yet
supported. Unsupported requests return an error; no renderer is connected.
Address placement has a bounded search and can fail under fragmentation.

Validation: 17 Windows entry tests pass, including a synthetic test that writes
through one alias and reads the same bytes through another. With the validated
USA 1.03 native image, execution passes the direct-memory-size query and stops at
`sceKernelMapFlexibleMemory` (`IWIBBdTHit4`, caller offset `0x207dbc`) during libc
initialization. Original game entry, graphics and the menu remain untested.


### Flexible memory (October 13, 2026)

Flexible memory now has a separate 448 MiB budget backed by zero-initialized
private Windows allocations. Supported CPU protections are translated to Windows
page protections. Mapping without a placement flag chooses a low address; fixed
mapping (`0x10`) supports free ranges aligned to Windows' 64 KiB reservation
granularity. Existing mappings are never replaced. GPU protection bits, occupied
fixed ranges and partial release remain unsupported. Both the flexible-specific
release and generic unmap update the budget only after a successful host release.
Named mappings share the same implementation; names are diagnostic metadata only.

The 17 Windows entry tests pass, with additional checks for zero-fill, allocation
isolation, budget rejection, fixed address placement, collision rejection and
stale/incorrect releases. The actual USA 1.03 libc initialization successfully maps
293601280 bytes (280 MiB) at its requested fixed address. The next unsupported call
is `scePthreadAttrInit` (`nsYoNRywwNg`, caller offset `0x5b42958`). Native module
initialization is still incomplete; original game entry and the menu have not run.


### Thread attributes (October 13, 2026)

A synchronized Windows attribute registry now implements initialization,
destruction, stack/guard sizes, detach state, scheduling policy/inheritance,
priority and affinity fields. Defaults and ABI identities follow the existing
Windows reference runtime. Settings are stored for future thread creation;
scheduling and affinity are not applied to host threads. Unsupported thread
creation and thread-attribute snapshots remain unresolved. Monotonically assigned
opaque handles prevent destroyed handles from becoming valid after slot reuse.

All 18 Windows entry tests pass. Attribute coverage includes defaults, field
round trips, invalid inputs, independent objects and stale-handle rejection.
The validated USA 1.03 native initialization now stops at `scePthreadSelf`
(`aI+OeCz8xrQ`, caller offset `0x5b42963`), after mapping its 280 MiB flexible
allocation. A guest thread identity must be integrated with the Windows TLS
record before proceeding. Original game entry and the menu have not run.


### Current-thread identity (October 13, 2026)

`scePthreadSelf` now returns an opaque record owned by the current Windows TLS
attachment. The TCB's thread field points to that same record, whose first field
points back to the TCB. Repeated calls are stable; separate host threads have
separate identities. Detach clears the TLS slot before freeing the record.
The record is valid only during its attachment; joinable thread lifetime, thread
creation, and a process-wide thread registry remain unimplemented.

The 18 Windows entry tests cover self resolution, TCB agreement, cross-thread
isolation and detach, alongside existing attributes and memory tests. Actual USA
1.03 libc initialization passes `scePthreadSelf` and stops at `scePthreadAttrGet`
(`x1X76arYMxU`, caller offset `0x5b4296f`). The next step is reporting validated
attributes for the running thread. Original game entry and the menu have not run.


### Current-thread attributes and native initializer completion (October 13, 2026)

`scePthreadAttrGet` now snapshots the current attached thread into an existing,
validated attribute object. Its stack size comes from Windows stack limits and
VirtualQuery's reservation base. Scheduling fields represent the documented guest
default profile; PS4 scheduling is not enforced. Host-owned threads have no runtime
requested guard size. Other-thread snapshots return a no-such-thread error until
a synchronized thread registry exists. Output handles retain their identity.

All 18 Windows entry tests pass, including comparison against the actual Windows
stack reservation, output isolation, invalid output handles and invalid thread
identities. The validated USA 1.03 diagnostic now completes both native module
initializers (libc and Fios2), each returning zero, and enters original game code
at offset `0xa0`. It registers 1934 exit callbacks and creates the EOP queue before
stopping at `_write` (`FxVZqBAA7ks`, caller offset `0x5b70427`, descriptor 1).
This is original-entry execution with linked native libraries, not menu or gameplay
compatibility. No GPU integration is enabled. Console output is the next blocker.


### Console output and first main message (October 13, 2026)

The diagnostic implements `_write` for guest descriptors 1 and 2 using Windows
standard handles, preserving binary bytes and reporting actual partial writes.
Other descriptors fail with EBADF; null nonempty buffers and oversized requests
are rejected. `__error` exposes thread-local POSIX errno storage. Host write
failures currently map to EIO. This is console-only support, not a guest filesystem.

All 19 Windows entry tests pass, including captured stdout/stderr separation,
embedded NUL bytes, zero-length writes and rejected arguments. The validated USA
1.03 target completes both native initializers and now prints its original
`trico main() start...` banner. Immediately afterward the process terminates with
Windows access violation `0xc0000005`; the existing exception diagnostic does not
produce a fault address for this case. The cause is not yet established. This
must be investigated before claiming further startup progress. Graphics, menu and
gameplay remain unavailable.


### Local stack commitment diagnosis (October 13, 2026)

The post-banner access violation was reproduced with the locally built Zig
executable: its PE header reserved 16 MiB of stack but committed only 4096 bytes.
Changing only the generated executable's stack commitment to 16 MiB lets the
same prepared game image advance without that fault. Guest code makes large stack
adjustments without Windows stack probes. No game instructions were patched.

The GitHub Clang build already requested a 16 MiB reserve and commit. The new
`tools/configure_probe_stack.py` normalizes those PE32+ fields after compilation,
including local builds, and rejects malformed or non-AMD64 images. Run it on
`out/tlg-entry-probe.exe` after rebuilding locally. Use only before binary signing;
modifying PE headers invalidates any existing signature. Generated binaries remain
untracked and no game executable should be passed to this tool.

Validation: two PE-header tests and all 19 Windows entry tests pass. With the
normalized local build the target prints its startup banner and stops normally
at unresolved `sceKernelReadTsc` (`-2IRUCO--PM`, caller offset `0xd16a4a`), with
exit code 20. The prior raw access violation is no longer observed in this run.
Timing APIs are the next blocker; graphics and menu remain unavailable.


### Hardware timing (October 13, 2026)

`sceKernelReadTsc` reads the actual x86 hardware counter, preserving consistency
with guest RDTSC instructions. `sceKernelGetTscFrequency` returns a frequency
calibrated once against Windows QueryPerformanceCounter over a 20 ms interval.
`sceKernelGetProcessTime` reports monotonic elapsed microseconds from runtime clock
initialization. Integer scaling uses 128-bit intermediates to avoid overflow.
Initialization is synchronized and fails explicitly if Windows clock queries fail.
This is a measured host frequency, not a claimed PS4 clock rate. Calibration noise,
non-invariant TSC hardware and virtual-machine migration remain limitations.

All 20 Windows entry tests pass, including hardware-counter advancement, stable
reported frequency and elapsed-time agreement with QPC. The USA 1.03 target now
passes the previous timing import and stops at POSIX `clock_gettime`
(`lLMT9vJAck0`, caller offset `0x5b7bdda`), requesting guest clock ID 13 (SECOND).
Clock-ID translation and explicit guest timespec layout are the next step.
Graphics and menu remain unavailable.


### Guest clock translation (October 13, 2026)

POSIX `clock_gettime` now writes an explicit 16-byte guest timespec containing
signed 64-bit seconds and nanoseconds. Realtime IDs 0/9/10 use Windows precise
UTC time converted from the FILETIME epoch to Unix time; ID 13 (SECOND) truncates
nanoseconds to zero. Monotonic/uptime IDs 4/5/7/8/11/12 use QPC with its actual
frequency. FAST/PRECISE aliases currently share the same source. CPU and network
clocks are rejected rather than substituted. Errors set thread-local POSIX errno,
and rejected clock IDs leave the output unchanged.

All 21 Windows entry tests pass, covering layout, epoch conversion, SECOND
truncation, monotonic advancement, aliases and invalid requests. USA 1.03 startup
passes the clock query and next stops at `scePthreadMutexattrSetprotocol`
(`1FGvU0i9saQ`, caller offset `0xd16d5e`). Mutex scheduling protocol semantics
are the next blocker. No graphics, menu or gameplay are available.


### Mutex protocol and first file-open blocker (October 13, 2026)

`scePthreadMutexattrSetprotocol` now validates registered attribute handles and
supports protocol NONE (0), matching the existing locks' behavior. Protocols
INHERIT/PROTECT (1/2) return ENOTSUP, rather than claiming priority inheritance or
priority ceilings. Invalid values and handles return EINVAL. No scheduling
behavior has been added.

All 21 Windows entry tests pass, including NONE, unsupported priority protocols
and invalid handles. The validated USA 1.03 target proceeds without requesting an
unsupported priority protocol, then stops at `sceKernelOpen` (`1G3lF1Gg1k8`, caller
offset `0x5c48f6a` in Fios2). Guest file-path translation, descriptor ownership and
file access are the next integration step. Graphics and menu remain unavailable.


### Initial read-only file access (October 13, 2026)

Set `TLG_GAME_ROOT` to the extracted game directory before running the diagnostic.
`/app0/`, `/hostapp/` and relative paths resolve against that directory. The initial
backend implements read-only open, read, 64-bit seek and close with private,
non-reused descriptor IDs and synchronized host-handle ownership. It rejects write
flags, unsupported mounts, dot/traversal components and Windows path separators,
colon and wildcards. Host path conversion currently uses the Windows ANSI code
page; Unicode paths and reparse-point containment are not implemented. This is not
a complete filesystem or a security boundary for untrusted game files.

All 22 entry tests pass, including byte-exact reads, seek, EOF, stale descriptors,
read-only rejection and unchanged fixture contents. USA 1.03 first requests the
relative optional file `memory.cfg`, then advances to `sceSysmoduleLoadModule`
(`g8cM39EUZ6o`, libSceSysmodule, caller offset `0xd4c9ae`, module ID `0xb4`).
2348 exit callbacks are registered at that point. No game archive loading or
rendering has been demonstrated. Module-loading semantics are the next blocker.


### Limited AppContent lifecycle (October 13, 2026)

Module ID `0xb4` is AppContent. The Windows diagnostic now provides a narrow host
implementation with synchronized load/reference counting, loaded queries, unload,
and reserved-zero initialization using the existing runtime's 32-byte input and
40-byte output ABI. Unknown modules are rejected. Initialization requires a load,
rejects nonzero reserved input, and resets after the final unload. Canonical
resolution requires the exact Sysmodule or AppContent library/module identities.
This does not load an absent PRX or implement all system modules. Application
parameter queries, add-ons and entitlement handling remain unresolved.

All 23 Windows entry tests pass, including reference lifetime, initialization
output boundaries, invalid reserved fields and reset after unload. The validated
USA 1.03 target completes AppContent initialization and stops at
`sceAppContentAppParamGetInt` (`99b82IKXpH4`, caller offset `0xd4c9e5`), requesting
parameter ID 1. The next step is validating that parameter against the supplied
content metadata rather than guessing a response. No graphics or menu are enabled.


### Metadata-backed application parameters (October 13, 2026)

Run `python tools/prepare_content_parameters.py <game-directory>` before the
linked diagnostic. It validates TITLE_ID CUSA03627 / APP_VER 01.03 and extracts
all four USER_DEFINED_PARAM fields into ignored `out/tlg/content-parameters.bin`.
An alternative path can be selected with `TLG_CONTENT_PARAMETERS`. The Windows
loader validates the fixed binary format, exact title/version and length before
serving AppContent IDs 1-4. ID 0 (SKU) remains unsupported: no license state is
inferred. Queries require a loaded and initialized provider. Invalid requests
leave output unchanged; absent or invalid prepared metadata stops explicitly.

Validation: 23 Windows entry tests and two metadata-format tests pass. USA 1.03
queries return SFO values 1, 1612131828 and 0 for IDs 1, 2 and 3 respectively.
Startup next stops at `sceSystemServiceParamGetInt` (`fZo48un7LK4`, caller offset
`0xd4ca5c`), requesting system parameter 1. That system setting must be handled
separately from application metadata. Graphics and menu remain unavailable.


### Explicit diagnostic language profile (October 13, 2026)

SystemService parameter ID 1 is the system language. The Windows diagnostic now
returns an explicit English US profile (value 1), following the existing runtime's
language convention and shadPS4's SystemService parameter IDs. This is a diagnostic
setting, not a value inferred from SFO or Windows locale. Other system settings
remain unsupported and return the parameter error without changing output.
Canonical dispatch requires libSceSystemService@1 / libSceSystemService@257.

All 24 Windows entry tests pass, including the language profile, null output and
unknown parameter rejection. USA 1.03 startup passes the language query and stops
at `sceKernelCreateSema` (`188x57JYp0g`, caller offset `0xdd53a1`). Semaphore
creation, wait, signal and lifecycle support are the next integration task.
Graphics and menu remain unavailable.


### Windows counted semaphores (October 13, 2026)

The diagnostic now implements semaphore create/delete, counted wait/poll and
signal with private 32-bit IDs, synchronized ownership and FIFO waiter ordering.
Multi-token waits consume their entire requested count atomically. Signals cannot
overflow the configured maximum. Timeouts use monotonic QPC deadlines with
millisecond Windows waits rounded upward; remaining time is reported in guest
microseconds. Deletion wakes blocked waiters and defers freeing the object until
they return. Priority ordering (attribute 2), creation options and cancellation
remain unsupported rather than approximated.

All 25 Windows entry tests pass, including a real blocked worker receiving two
separate signals, poll fairness, timeout, isolated counts, overflow, stale IDs and
deletion waking a blocked worker. USA 1.03 creates a semaphore with initial count
0 and maximum 2147483647, then stops at `scePlayGoInitialize` (`ts6GlZOKRrE`,
libScePlayGo@1 / libScePlayGo@256, caller offset `0xdd542f`). PlayGo installation
state handling is the next blocker. Graphics and menu remain unavailable.


### PlayGo metadata initialization (October 13, 2026)

PlayGo initialization now validates its explicit 16-byte input ABI, non-null
workspace, minimum 2 MiB workspace size and zero reserved field. It reads the
local `/app0/sce_sys/playgo-chunk.dat` header, checks its magic, declared file size
and nonzero chunk count, then records initialized state. Open validates pointers,
parameters and lifecycle. Canonical resolution requires libScePlayGo@1 /
libScePlayGo@256. Initialization does not claim that declared chunks are installed;
workspace management, full metadata parsing and availability queries remain incomplete.

ABI/error references: [shadPS4 PlayGo types](https://github.com/shadps4-emu/shadPS4/blob/main/src/core/libraries/playgo/playgo_types.h)
and [implementation](https://github.com/shadps4-emu/shadPS4/blob/main/src/core/libraries/playgo/playgo.cpp),
GPL-2.0-or-later, Copyright 2024 shadPS4 Emulator Project.

All 26 Windows entry tests pass, including initialization validation, malformed
metadata rejection and open lifecycle. The USA 1.03 target reads its actual
1632-byte PlayGo metadata file declaring 27 chunks, initializes and opens PlayGo,
then stops at `scePlayGoGetLocus` (`uWIYLFkkwqk`, caller offset `0xdd54a4`).
Determining actual local chunk availability is the next blocker. No graphics or
menu are available.


### PlayGo availability investigation (October 13, 2026)

`tools/inspect_playgo.py` validates the metadata header, table bounds, chunk and
microchunk attribute sizes, chunk reference indices and terminated labels. It
writes an ignored inspection report containing package ranges. Three synthetic
tests cover valid mappings, truncated/out-of-bounds data and invalid references.
The tool does not fully validate scenarios or inner microchunk tables.

The actual USA 1.03 file declares 27 logical chunks referencing only two physical
microchunks. Those microchunks describe offsets and sizes in the original package,
not paths in the extracted game directory. Required locus is a requested target
state, not evidence of current availability. Therefore neither the header count
nor required-locus fields justify reporting every chunk as LocalFast.

Format reference: [shadPS4 PlayGo chunk structures](https://github.com/shadps4-emu/shadPS4/blob/main/src/core/file_format/playgo_chunk.h),
GPL-2.0-or-later, Copyright 2024 shadPS4 Emulator Project.

Runtime behavior is unchanged and remains blocked at `scePlayGoGetLocus`. The next
step is identifying a reliable correspondence between package regions and the
extracted file set, or defining an explicit offline installation profile with
clearly stated validation limits. No graphics/menu progress is claimed.


### Explicit offline PlayGo assumption (October 13, 2026)

The disc maps contain binary package layout records; no reliable mapping to
extracted paths has been established. To investigate subsequent startup stages,
the diagnostic now offers an opt-in assumption profile:
`$env:TLG_PLAYGO_ASSUME_LOCAL='1'`. It reports requested valid chunk IDs as
LocalFast, explicitly assuming the user's extracted copy is complete. This does
not verify completeness, file integrity, package ranges or download state, and
must not be described as validated installation availability. The default profile
returns NOT_SUPPORT_PLAYGO and leaves output unchanged.

`scePlayGoGetLocus` validates lifecycle, handle, pointers, count and every chunk ID
before writing any output. Errors preserve output. All 26 Windows entry tests
pass, including disabled/enabled profiles, invalid IDs and unchanged error output.
With the explicit assumption enabled, USA 1.03 requests all 27 chunks, proceeds
to the Fios2 SDK banner, then stops at `scePthreadRwlockInit` (`6ULAa0fq4jA`, caller
offset `0x5c4a4c1`). This is conditional startup progress; validated PlayGo
availability remains unfinished. Graphics and menu remain unavailable.


### Reader/writer synchronization (October 13, 2026)

The Windows mutex backend now provides explicit rwlock initialization/destruction,
read/write lock, try-read/try-write and unlock. A synchronized registry uses
non-reused opaque IDs, counts readers per host thread, excludes writers, detects
writer recursion/read-to-write upgrades and rejects foreign unlocks. Existing
readers may recursively lock; waiting writers receive preference over new readers.
Destruction is rejected while owned or while threads are waiting. Limits are 128
objects and 64 simultaneous reader owners per object. Timed locks and custom
attributes remain unsupported.

All 26 Windows entry tests pass, with added concurrency coverage for overlapping
readers, a blocked writer, independent objects, ownership, recursion, busy
destruction and stale handles. With the explicit offline PlayGo assumption enabled,
USA 1.03 Fios2 passes rwlock initialization, then requests mutex priority protocol
1 (inheritance). The backend returns ENOTSUP and Fios2 executes an illegal
instruction at guest offset `0x5c4a2f5`; the diagnostic reports exception
`0xc000001d`. This failure is attributable to a required synchronization contract,
not a missing rwlock export. Priority inheritance needs a coherent implementation
or a separately documented approximation before proceeding. No graphics/menu.


### Opt-in mutex priority fallback (October 13, 2026)

`TLG_MUTEX_PRIORITY_FALLBACK=1` explicitly permits protocol INHERIT attributes to
create ordinary owned mutexes for startup investigation. The requested protocol
is retained on the attribute and copied into the lock. Each affected lock logs
that priority inheritance is unavailable. Exclusion/ownership/recursion behavior
remains active; priority donation and PS4 scheduling are not implemented. Protocol
PROTECT remains rejected. The default still rejects unsupported priority protocols.
This approximation can cause priority inversion or scheduling differences and
must not be described as working priority inheritance.

All 27 Windows entry tests pass, including strict/fallback profiles, protocol
retention, basic locking and priority-ceiling rejection. With both the offline
PlayGo assumption and mutex fallback enabled, USA 1.03 Fios2 creates five affected
mutexes and reaches `scePthreadCreate` (`6UgtwV+0zb4`, caller offset `0x5c4a892`).
Guest thread creation with correct TLS, stack and lifetime is the next blocker.
This remains conditional startup progress; graphics and menu are unavailable.


### Joinable Windows guest workers (October 13, 2026)

`scePthreadCreate` now creates suspended Windows workers, publishes their opaque
records, then resumes them. Each worker attaches a private copy of the configured
main TLS template and binds its thread record into the TCB before invoking the
SysV guest entry. Normal return records the result and releases TLS. Join waits
for host completion, returns the guest result and closes the host handle; a bounded
record tombstone prevents pointer-handle reuse. Self and equality use the same
identity. Windows receives the requested committed stack size (16 KiB-64 MiB).
There is a lifetime limit of 256 created worker records.

Only joinable threads returning normally are implemented. Detached threads,
custom guard sizes, explicit guest pthread exit, cancellation and PS4 scheduling/
affinity enforcement remain unsupported. Main-template configuration must occur
before publishing workers; dynamic module templates remain immutable thereafter.

All 28 Windows entry tests pass, including a real SysV worker, TLS template copy
and isolation, TCB/thread identity, result propagation and stale join rejection.
With both experimental profiles enabled, actual USA 1.03 Fios2 workers execute and
concurrently reach `scePthreadCondWait` (`WKAXJ4XBPQ4`, caller offset `0x5c49ef4`)
and `scePthreadCondBroadcast` (`JGgj7Uvrl+A`). Stop messages may interleave across
threads. Condition waiting/broadcast with atomic mutex release/reacquisition is
the next blocker. Graphics and menu remain unavailable.


### Condition waits and notifications (October 13, 2026)

The Windows mutex backend now implements condition wait, signal and broadcast.
A common SRW state lock makes guest mutex release and wait registration atomic.
Wait returns only after reacquiring the guest mutex. Condition/mutex waiter
references prevent destruction while sleeping or reacquiring. Foreign-owner waits,
recursive depth greater than one and inconsistent mutex binding are rejected.
Timed waits, cancellation and recursive-depth restoration remain unsupported.

All 28 Windows entry tests pass, with added checks for two broadcast waiters, a
single signaled waiter, mutex reacquisition, busy destruction and stale conditions.
With both experimental profiles enabled, USA 1.03 passes the previous missing
condition imports, then Fios2 executes UD2 at guest offset `0x5c4a339` (exception
`0xc000001d`). Inspection shows that this assertion follows a thread-identity
comparison and a synchronization call; which condition failed is not yet known.
Do not treat this as completed Fios2 startup. Thread ownership/identity integration
is the next investigation. Graphics and menu remain unavailable.
